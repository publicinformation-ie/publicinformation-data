# Design

## Context

See `proposal.md` — Why. Three constraints shape the approach:

- The dataset is generated by `scripts/build_transport_raci.py` and published under
  `public/latest/transport-raci/` with one table per axis and a sparse assignment matrix.
  The vocabularies are generated too, so the skill can point at them without a second
  writer.
- `pipelines/spc_pipeline/reference/transport_subdomains.json` is already the single
  committed source for the 17 subdomain terms; `build_vocabularies.py` writes the CSV from
  it and `extraction.py` feeds it to the model as a closed list.
- `extract_spc_items` produces decisions, item keys and transport topics in one model
  call, so re-running it to change only the tag vocabulary would churn every published
  record.

## Goals / Non-Goals

**Goals:**

- One description of transport governance in the repository: the dataset. The skill and
  the SPC tags both read from it.
- No paid step and no change to any decision, item key or attendance record.
- A reader of the old vocabulary learns, at the old URL, that it is retired and what
  replaces each term.

**Non-Goals:**

- Re-tagging the SPC items with model judgement at grouping or activity level.
- Assessing councils other than Meath.
- Resolver pages or DCAT records for the four transport RACI vocabularies; a location URI
  for `dct:spatial`.

## Decisions

### The skill reads the dataset at answer time

`SKILL.md` routes a question to (activity, stage), then points at
`public/latest/transport-raci/raci-wide.csv` (one line per assignment, plain party names
in the `R`, `A`, `C`, `I` columns) and `assignment-roles.csv` (party URIs) for the answer,
and at `public/vocabularies/*.csv` for the terms. The 385-line `raci-gda.md` is deleted
rather than regenerated: a second table would be a second copy to keep in step, and the
dataset already ships a readable line per assignment.

`vocabulary.md` shrinks to the question vocabulary the dataset does not publish: aliases
lay readers use (`public transport`, `Part 8`, `s.38`), the banned-terms table, and a
pointer to the published vocabularies for every definition. `checks.md` keeps its
procedure but its expectations become dataset rows.

### The crosswalk lives with the term list

`transport_subdomains.json` gains `grouping_ids` per entry, so the mapping sits beside the
term it maps and cannot drift from the vocabulary that `build_vocabularies.py` writes. A
separate CSV would be a second list to keep in sync. The file records that it is frozen:
the classification step still reads it, so it is not deleted.

Mapping, in full:

| Retired term | Grouping(s) |
|---|---|
| `infra/national-roads`, `infra/regional-local-roads` | `RT1` |
| `infra/active-travel` | `RT2`, `RT3` |
| `infra/bus` | `RT4` |
| `infra/heavy-rail` | `RL1` |
| `infra/light-rail` | `RL2` |
| `infra/kerbside` | `RT7` |
| `infra/ports-airfields` | `WT1`, `AT1` |
| `svc/pso-bus`, `svc/commercial-bus`, `svc/spsv` | `RT5` |
| `svc/rail` | `RL3` |
| `svc/light-rail` | none: the new model has urban rapid transit infrastructure (`RL2`) but no services grouping |
| `svc/school-transport` | `X6` |
| `svc/shared-mobility` | `RT5` |
| `users/vehicles-drivers` | `RT8` |
| `users/traffic-law` | `X1` |

Two terms map to two groupings because the retired term conflated them (`active-travel`
covers paths and lanes; `ports-airfields` covers ports and airports). Splitting is honest
about the source term's ambiguity; the README says so. One term has no replacement, is
recorded as such with its reason, and fails the export if a future run ever emits it,
rather than being coerced onto the nearest grouping.

### `groupings` replaces `subdomains` outright

Keeping `subdomains` alongside a deprecated field was rejected: the two would say nearly
the same thing, and every consumer would have to choose. The removal is a MAJOR version
(`2.0.0`) under the project's SemVer rule for breaking schema changes, with the previous
release left in place.

### The retired vocabulary keeps its URLs

`transport-subdomain.csv` and its CSVW metadata stay exactly as they are, because they
are published URLs that consumers may parse. What is added is the machine-readable
retirement: `transport-subdomain.ttl` with `owl:deprecated` and `dct:isReplacedBy` per
term, `transport-subdomain.md` as its human page, and a resolver page at
`ns/transport-subdomain/` so the term URIs finally dereference to the retirement notice.
`build_vocabularies.py` writes all three, so the SPC pipeline stays the only writer for
this vocabulary.

## Risks / Trade-offs

- **Coarser tags.** National and regional roads both become `RT1`; an `active-travel` item
  appears under both walking and cycling. → The README states that groupings are mapped
  from the earlier subdomain tagging and are coarser than the retired terms. A future
  change can re-tag with model judgement if the coarseness proves a problem.
- **The classification prompt still speaks subdomains.** The step's closed list is
  unchanged, so the pipeline internally uses a retired vocabulary. → The reference file is
  marked frozen and the step README says the export maps it; a future re-run still works,
  and an unmapped tag fails closed.
- **The skill is thinner than the old GDA claims.** Many rows are not assessed, and only
  Meath is analysed. → The caveat requirement and the gap rule make that explicit; the old
  table is deleted so nothing competes with the data.
- **A skill that drifts.** Routing prose is hand-written. → `checks.md` holds a question
  set whose expected rows a test verifies against the published dataset, so a vanished row
  fails CI.

## Migration Plan

1. Publish the vocabulary retirement and the crosswalk, then rebuild the SPC dataset as
   `2.0.0`. `latest` moves with it; `v1.2.0` is untouched.
2. Rewrite the skill against the new fields in the same commit, so no commit leaves the
   skill reading `subdomains`.
3. Rollback is a revert: `v1.2.0` and the old vocabulary files remain published, and the
   dataset is reproducible from committed inputs.
